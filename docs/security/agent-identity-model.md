# Arqon Maestro: Agent Identity and Trust Model

## Purpose
This document defines the strict architectural boundary between Human Operators and Agents within Arqon Maestro. It ensures that Agent identities are never conflated with Human identities, and that Agent voices (personas) are never mistaken for authentication factors.

## 1. The Human-Agent Duality
Maestro recognizes two distinct classes of principals. They operate on separate trust planes and possess different factor requirements.

| Characteristic | Human Operator | Agent / Service |
| :--- | :--- | :--- |
| **Root Trust** | Passkey (WebAuthn/FIDO2) | Cryptographic Workload Identity |
| **Continuity** | Local Device-bound PIN | Signed Session Tokens / JWTs |
| **Attribution** | Live Voice Verification | Cryptographic Signing / Hash |
| **Voice Role** | Authentication Factor | Persona / Text-to-Speech (TTS) |
| **Session Join** | Participants Popup (Passkey) | Automated Scoped Authorization |

---

## 2. Agent Identity Laws

1.  **Identity Law:** Agent identity is established via cryptographic workload credentials, never via voice characteristics.
2.  **Persona Law:** An agent's voice is a "Persona" only. Hearing an agent's voice does not imply the agent has been authenticated.
3.  **No Factor Law:** Agents do not possess Passkeys or PINs. They are never prompted for human authentication factors.
4.  **No Room Join Law:** Agents do not "Join" a Multi-User Room via the Participants roster. They operate in a separate "Workload Plane" with scoped authorization.
5.  **Audit Law:** Every agent action must be logged with its cryptographic Workload ID, not its Voice Persona name.
6.  **Symmetry Law:** Agents may speak to humans, but they must never use a human profile's voice characteristic (cloning) to authorize an action on behalf of that human.

---

## 3. The Agent Trust Plane

### Root Trust: Workload Identity
Agents authenticate to the Maestro runtime using industry-standard cryptographic methods (e.g., SPIFFE IDs, X.509 Certificates, or signed API keys). This identity is verified at the system level before the agent is allowed to participate in any workflow.

### Authorization: Scoped Capability
Once an agent is identified, it is granted a **Capability Scope**. This defines:
*   Which Arqon subsystems it can interact with.
*   Which human profiles it can "observe" (for context-aware assistance).
*   Whether it can initiate "Suggested Actions" that require human approval.

### Agent-to-Human Handoff (The Approval Gate)
When an agent performs a task that crosses into **Operational** or **High-Risk** territory, the trust model shifts:
1.  The Agent proposes the action.
2.  Maestro identifies the action as requiring human authorization.
3.  The **Human Operator** (currently Active in the room) must authorize the agent's action using their own factors (Voice, PIN, or Passkey depending on risk).

---

## 4. Voice Persona Specifications

### Persona Labels
In the UI and within the logs, an agent's voice must always be referred to as a **Persona**.
*   *Correct:* "Persona: Linter-Voice-Alpha"
*   *Incorrect:* "Identity: Linter"

### Persona Assignment
Humans (with appropriate Policy Tiers) can assign personas to agents. This is a cosmetic preference, not a security mutation.
*   Assigning a voice to an agent does *not* grant the agent human-level privileges.
*   Multiple agents can share the same persona, but they must maintain unique cryptographic Workload IDs.

---

## 5. Security Gotchas & Countermeasures

*   **Gotcha: Agent Impersonation.** An agent might attempt to "speak" a command that sounds like a human operator to trick the diarization engine.
    *   *Countermeasure:* Maestro's audio-loopback-cancellation and internal routing ensure that speech generated by the system (TTS) is never fed into the Voice Verification engine as an external "Live Speaker."
*   **Gotcha: Personification Bias.** Humans may trust an agent more because it has a friendly voice persona.
    *   *Countermeasure:* The UI must always display a clear visual indicator (e.g., an Agent Badge) when an agent is speaking or proposing an action, regardless of how "human" the voice sounds.
*   **Gotcha: Credential Bleed.** Developers may try to give an agent a "Profile" so it can log in like a human.
    *   *Countermeasure:* This is strictly forbidden. Agent identities are technically distinct and cannot possess `passkey_ready` or `pin_ready` states in the database.
